# 项目现状与取舍

本项目已确认定位为 **Agent 评测工作台**：用固定任务运行被测 Agent，保存评分和原始证据，再比较不同运行的表现。当前要先恢复项目所有者对主流程和缺陷的理解，据此决定保留、简化或复用哪些部分。

自动生成评测题已排除出产品方向；相关旧模块尚未因此删除。目标是建立经人工核验的固定 golden set（基准任务集），现有20题还不能直接获得这个身份。

核查日期：2026-11-17。本页区分代码现状、用户已确认方向和待选建议；不是实施计划、评分校准结果或新的模型评测报告。

## 当前最重要的三个缺口

### 1. 题集还不足以承担可信、可移植的基准

现有20题尚未经过难度校准，公开包没有移植完整原评分器和统一实跑器；环境材料也不是逐题在新机器重建过的历史锁文件。当前执行适配的 `default_binding()` 仍默认指向仓库外的本机冻结入口、题库与 Harness 源码，`execution_files()` 还读取外置评分脚本和依赖。

这意味着“材料公开了”“本机跑过了”和“别人能重建同一测量”是三件事。已有每题独立进程、工作区和原生权限边界；缺的是可重建性与测量校准，不能写成没有隔离。

证据：[20题材料及发布边界](../examples/eval/formal20/README.md)、[默认绑定及材料指纹](../scripts/formal20_runtime.py)（`BASE`、`default_binding`、`execution_files`）、[执行器边界](../scripts/README-formal20-concurrent.md)。

### 2. 部分原判据没有完成语义验收，后续报告不会补齐

本机外置原评分器中，部分解释类检查会留下 `unknown` 等待复核。例如 `formal-anchors.py` 的 `localization`，以及 `formal-evidence.py` 中 C01 的 `causal_explanation`、O02 的 `version_interpretation`。`formal-engineering.py` 的 `report` 只检查文件存在且大小大于零，不能证明报告内容正确。

平台已有原自动值、复核值和未判定状态的分别保存；并非所有题的最终结果都必然是 `unknown`。但对比统计只投影保存的原判据，报告提交检查主要保证结构、范围与证据引用，均不能自动补成新的语义评分或根因验证。

证据：[原评分器调用位置](../scripts/formal20_runtime.py)（`runner.grade_case`）、[原判与复核的来源](JUDGE_EVIDENCE.md)、[统计实现](../backend/lab/comparisons/metrics.py)、[报告检查边界](CAPABILITY_REVIEW.md)。上述三个原评分脚本在本机仓库外，不能当作公开包已包含的能力。

修改范围也需要按题审查：当前外置工程评分器允许新增符合命名规则的回归测试，不能把旧 `allowed` 字段机械地当成完整授权清单。U04 已有独立的范围复核规则，但它只另存复核结果，不改旧分数，也不证明其他题已校准。见 [U04 范围校准](U04_SCOPE_CALIBRATION.md)。

### 3. 新的运行与恢复链仍缺真实供应商验证

当前已有冻结计划、受控执行、账本、检查点恢复、归档及报告接续代码。相应集成测试使用真实冻结任务、Agent、工具和原评分器，但把 SDK 响应换成脚本；这能检查程序链路，不能证明真实供应商响应、配额、费用、模型行为或实际加速效果。

历史真实运行归档与新入口的验证范围要分开。已有真实归档，不代表新链路已经完成真实模型验收；支持 `provider_api` 也不等于已验证。新增“输出与恢复”资料同样明确真实模型调用为零，本轮没有重新运行其测试。

证据：[真实任务路径的脚本响应测试](../scripts/tests/test_formal20_real_path.py)、[原生多轮与恢复测试](../scripts/tests/test_formal20_native_recovery.py)、[日常交付与离线验证边界](REAL_RUN_DELIVERY.md)、[输出与恢复说明](OUTPUT_RECOVERY.md)。

## 主流程和模块依赖

先分清四个对象：**task** 是题目及环境、验收要求；**run** 是指定 Harness、模型和预算下的一次执行；**score** 是某版评分器对该次执行的判断；**evidence** 是支撑判断的原始轨迹、文件和检查结果。分析 Skill 和报告使用这些对象，不应替代它们。

当前日常入口仍把执行与报告交付接在一起：`evaluation.py` 预检平台、项目、固定 Skill 和基线配置，执行后自动归档并准备分析材料。同一发起者继续分析和提交报告。显式 `baseline_only` 可免 A/B 基线要求，但仍要求平台及固定 Skill。

“核心 task / run / score / evidence 可以独立于分析 Skill 和报告运行”是已确认方向，尚未在日常入口完成解耦。当前证据：[配置要求与启动预检](../scripts/evaluation.py)（`delivery_config`、`preflight`）、[后续交付](../scripts/formal20_pipeline.py)。

下表的“必需”指理解与完成核心评测所需的职责，不代表所有当前实现都必须保留。

| 模块 | 当前作用及依赖 | 取舍状态 |
| --- | --- | --- |

## 已确认的方向

- 产品主线围绕固定任务、受控运行、评分与证据；优先诊断题集、执行和最终评分。
- 排除自动生成评测题；固定 golden set 需要人工核验，不能用题数代替可信度。
- 核心评测应能独立于分析 Skill 和报告；单题执行不以先发布分析方法、建立 A/B 或提交报告为前提。现有代码仍有前述差距。
- 允许研究复用或替换部分自研模块；没有决定采用哪个框架、迁移哪些部分或删除哪些模块。
- 先贯穿一道真实任务，查清题面、环境、执行、判分、证据展示和两次实验比较，再判断问题是否普遍存在。
- 后续重要开发开始前说明为何改、影响主流程哪里；完成后用实际例子和证据解释变化，并更新现状文档。小修按影响缩减说明。

这些方向不等于已批准模型调用、正式重跑、修改原评分、覆盖历史数据、模块裁剪或框架迁移。

## golden set：核对项已确认，具体门槛未定

这里的 golden set 是**被测 Agent 的固定基准任务集**。用于校准评分器的人工好坏样本可以关联到它，但两者不是同一个对象。

每道候选任务至少要核对：

1. **代表什么能力、难点在哪里。** 有明确来源和用途，不仅有难度标签。
2. **环境能否重建。** 输入、依赖、准备步骤、执行控制及隔离要求完整，版本可固定。
3. **题面与验收是否一致。** 不增加未告知的限制；工程任务允许多种正确实现，不要求逐字匹配参考补丁。
4. **评分能否区分已知正确与错误方案。** 包括合理的替代实现、关键失败和边界情形；语义项有可复核依据。
5. **结果能否回查。** 保存评分器版本、判据、原始证据和复核来源，区分任务失败、未判定及环境/评分异常。

具体题单、覆盖维度、规模、难度分布、校准方法、一致性及稳定性阈值仍未定案。现有20题是候选材料来源，不是已通过这些门槛的结论。

## 评分取舍：先分三部分，再决定尺度

已确认要分别表达：**整体任务验收、各维度量化表现、未判定及运行/评分异常**。这样才能看出功能完成却交付违规、评分证据不足或环境故障等不同情况。

尚未决定统一采用 0/1、1—10 或其他尺度，也未决定加权总分、rubric（各项评分规则）、分档锚点和聚合方式。当前已有的 0/1/unknown 检查和统计口径是现状，不能直接当成未来评分制度。

同样，工具错误数不能直接代表恢复能力，长度不能直接代表简洁度，哈希相同不能证明内容真实，报告回执不能证明解释正确。哪些维度值得量化，要回到具体任务及可观察证据决定。

## 待选建议：用来帮助判断，不是已批准方案

- 可以借 [开源实现参考](OPEN_SOURCE_REFERENCES.md) 中的工作台对象、执行/评分边界和任务包组织方式，检查本项目缺什么；具体组件兼容性、Windows 成本和历史数据迁移尚未验证。
- 可以讨论把报告前置条件移出单题核心执行；这会影响启动预检、配置、状态和交付合同，不能只删除几行 Skill 校验。
- 可以讨论简化草案审批、Judge 或旧接口；应先查实际使用、数据引用和历史可读性。文件多、页面多本身不是删除依据。

本页没有选定框架、安排迁移、增设总分或列出待删除模块。

## 阅读顺序：先架构，再贯穿当前 U05

1. 先读 [架构与执行流程](../ARCHITECTURE.md)，找到执行端、平台端和证据存储的边界。
2. 再读当前 formal20 的 [U05 题面](../examples/eval/formal20/cases/U05/TASK.md)：给 CLI 增加只读 `/limits`，然后查看 [输入](../examples/eval/formal20/cases/U05/input) 与 [验收材料](../examples/eval/formal20/cases/U05/judge-only)。验收材料只供评测方查看，不能提前提供给被测 Agent。
3. 对照 [runtime](../scripts/formal20_runtime.py)、[归档转换](../scripts/formal20_archive.py) 和 [统计口径](../backend/lab/comparisons/metrics.py)，分别回答“实际跑了什么、谁判分、证据在哪里、哪些项不能比较”。公开材料不能代替本机历史原件。
4. 用一题的事实讨论取舍，再回到 [文档目录](README.md) 选择具体资料；不要求一次读完所有文件。

注意题号随历史题集变化：当前 formal20 的 U05 是 CLI `/limits`；[保存交付物的独立检查](SAVED_DELIVERY_CHECKS.md) 中的 U05 是旧 Click 默认值帮助任务，不能因为编号相同就沿用其检查包或结论。

## 本页证据边界

本轮只核对访谈、链接所指源码、外置原评分器片段和已有说明；没有运行任务、评分器、程序测试或真实模型，也没有重新验证输出恢复代码。旧文档与验证记录中的测试数、截图和结论保留其当时范围，不代表当前全部代码已重新验收。

静态代码能确认职责和规则，不能证明每个潜在问题都已造成实际误判；模块是否值得保留仍需结合具体使用和证据判断。
