# 通用 Harness 评测

把需求转成一份能够解释“选什么、为什么选、怎样改、怎样判断”的评测集草案。立足被测项目当前阶段，分别按用户需求和具体能力选题，再检索、筛选和适配已有案例；两类分别交付，通过需求与能力的关联保持联系，只为明确缺口补充设计。

这是可使用、待实际反馈调优的 v0.1.2。职责包括案例、预期、证据要求和覆盖说明；止于草案交付。真实执行、运行评分、根因归属、Harness 修改及版本比较由后续工作承担。构建过程的核对不称为独立质量验证。

## 1. 明确本次需求和边界

确认被测 Agent/Harness 的实际项目与版本，区分它、执行本 Skill 的 Coding Agent，以及存放评测集的平台；三者的工具和能力不能互相代用。“类似 Claude Code”等类比只说明方向，不能据此推定当前功能、环境或成熟度。

读取已有对话、项目说明、当前入口与工具定义，按需查循环、上下文、验收和恢复实现，以及已有任务和运行记录。优先使用已有信息，只询问会改变选例或预期的缺口。不要要求用户重新填写已知内容。

在检索前形成简短的项目现状说明：现在想完成的任务、实际可用工具和环境、已实现的机制、已有成功/失败证据、尚不清楚的能力。分别标注“源码中有实现”“离线契约有检查”“真实模型运行有证据”；它们不能相互替代，现有测试文件也不代表本轮已经运行通过。用户描述项目早期，不意味着所有能力都必须从最简单开始；以当前证据定位。

先写一段范围说明，包含：用户希望通过评测判断什么、任务载体、被测系统的工具与环境、支持的交互方式，以及已知限制。区分已确认事实、试用假设和待确认条件。

“长程”关注有前后依赖的动作、持续变化的任务状态和反馈下的推进，不仅是文本长、工具多或耗时长。分别标记：单次委托中的多步执行、用户多轮交互、跨上下文续接。前者不能自动代表后两者。

只有系统实际支持或明确承诺时，才选择压缩、Checkpoint、记忆、子 Agent、权限、预算等相关测试。尚未确认被测项目和关键能力边界时，可以整理来源及暂定方向，但不能把基于假设的案例确认为当前主选。已核对项目、仅剩接线细节时，可以继续内容筛选并具体标记待适配项；“待适配”不能代替场景和阶段匹配。

本次范围确认过就继续工作，不反复要求批准。确实需要用户决定的规则冲突或范围变化，明确列出并继续不受影响的选例工作。

## 2. 分别形成用户需求任务与具体能力专项

两类回答不同问题，选题依据和最终清单都要分开：

| 类别 | 要回答的问题 | 选题路径 |
|---|---|---|
| 用户需求任务 | 用户希望 Agent 做的事情，能否按要求完成？ | 已知需求与使用场景 → 任务、交付物及约束 → 保留真实依赖的案例 → 任务验收依据与证据 |
| 具体能力专项 | 某项能力在指定条件下，是否表现出所要求的行为？ | 能力目标 → 可观察性质与关键条件 → 合适的任务载体 → 专项判据与证据 |

需求类说明场景来自用户明确要求、已有实际任务，还是依据项目推定的候选。工具能承载某题不等于用户需要该场景；缺少需求依据时标为候选或覆盖缺口，不冒称已经代表用户真实需求。

按主要评测目的分类，不按长短、难度、轮数或是否涉及代码分类。短任务也可能直接对应用户需求，能力专项也可能需要完整多步任务。需求案例可以标注关联能力；能力专项可以复用需求案例的材料，但要说明专门观察的条件。共享材料或同一次运行不自动产生两份独立的覆盖证据。

确定维度与证据时读取 [评测维度与证据选择](references/evaluation-dimensions-and-evidence.md)。八项能力是候选目录，最终任务成果是共同观察项，不要求全部覆盖或平均配额。需要了解早期方法来源时再读 [候选能力与方法来源](references/capability-candidates.md)；来源不代替本次需求。

需求任务保留完整验收要求，能力专项明确主要测试点；两类都把预期依据与观察位置写具体。再用轻量的“需求任务—关联能力专项”对应关系连接，不能用一个混合清单替代两类结果。

推导时回答：哪条信息或前序产物会影响后续动作？什么条件变化会改变正确行为？从哪里能够判断这种差异？如果回答仍是“理解好不好”“规划是否合理”等宽泛表述，继续具体化。

例如，“处理中用户修改文件汇总规则”可拆成：使用已确认的新规则、保留其他有效限制、区分明确修改与假设讨论。需要原规则、修改出现的条件、后续可受影响的操作或成果。只有长对话而没有影响后续行为的信息，不足以承载这个测试点。

先列本次需要覆盖的测试点，不在检索前把所有案例写死。优先选择项目当前需要完成、且成败能为开发提供有用信息的任务，再按需要保留能力边界候选；不固定数量或难度比例。来源材料揭示歧义或遗漏条件时，可以修订测试点；不悄悄扩大已确认范围。

判断难度时看材料规模、必要依赖、规则或分支数量、反馈变化及领域知识要求；把任务本身的难度与搭建容器、外部服务、专用工具等接入成本分开。未执行前只作有依据的设计判断，不承诺通过率或宣称某题一定太难。可以降低无关专业知识与环境负担，但保留要观察的关键依赖，不把全部任务退化为单步调用，也不为“长程”人为增加步骤。

## 3. 检索来源，检查具体案例

优先复用开源评测中的案例；按需参考成熟项目的测试、Issue/PR 复现材料、已获准使用的真实任务与历史失败。已有人工认可的案例可以作为范例。项目知名度、榜单分数或“附带测试”本身不构成采用理由。

检索分两层：

1. **来源层**：确认评测用途、任务类型、材料入口、判定方式和复用条件，决定是否值得深入。
2. **案例层**：实际阅读具体任务、初始材料或其构造方式、环境定义、参考结果或检查逻辑。不能只根据 README 或任务名称认定案例可用。

用公开一手材料核对，优先固定到 commit、数据集版本及案例 ID。记录必要的文件或行位置。材料体积大、需要登录、依赖外部服务或未取得许可时，保留限制；不要为完成筛选擅自安装完整环境、申请账号或启动付费运行。

执行脚本、参考解和测试属于评判或审查材料，不能自动放进被测 Agent 的可见输入。用户已授权实际试用时，先完成可用信息下的筛选，不停在“推荐几个基准名称”。

## 4. 用四个维度作出选择

前三项主要审查具体案例，第四项审查集合。记录简短依据，不加权成统一置信度分数。

| 维度 | 要核实什么 | 如何据此处理 |
|---|---|---|
| 场景契合 | 实际任务结构、交互和依赖是否涉及本次测试点，适合当前项目阶段？主要难点是否属于当前关注范围，成败是否有助于开发判断？ | 契合则继续；局部契合可提取或适配；只有产品类型相似、却依赖未具备能力或过多无关难点则不作当前主选 |
| 预期可信 | 预期能否由明确需求、规则、工具契约或可靠材料推出？检查是否覆盖关键要求并允许合理替代方案？ | 核对任务与判定器，不默认测试脚本正确或完整。冲突、隐藏要求、弱检查先记录并决定补充或暂缓 |
| 条件可落地 | 输入、初始状态、工具、数据和观察材料是否可提供？成本及依赖是否适合目标环境？ | 条件已核实才可直接复用；改造路径明确则待适配；必要条件缺失则保留缺口 |
| 集合覆盖 | 新案例增加了什么重要条件？与已有案例是否重复、冲突或过度集中？ | 按新增覆盖价值选取，不把换名字、改措辞当新增能力覆盖 |

为每个进入实质检查的候选给出一种处理：

- **直接复用**：测试意图和判定适合当前需求，输入、环境与证据条件已核实兼容；说明尚未实际运行的验证边界。
- **需适配**：值得采用，但需要明确的工具、环境、数据或判定调整；具体写出改什么及待确认项。
- **暂不采用**：不契合、关键依据或材料缺失、适配会损坏测试意图，或没有新增覆盖价值；说明原因。

区分“已核实”“据材料推断”和“未知”。无法确认环境时，不把“仓库里有 Dockerfile”写成“已可在当前 Harness 运行”。即使暂不采用，也可以保留它对覆盖缺口的启发。

## 5. 适配并整理案例

先说明原案例的测试意图，再确定可变部分和必须保留的条件。

- 替换名称、格式或测试数据时，保留关键约束、依赖和信息关系。
- 对齐工具或环境时，核对动作语义、错误语义与状态变化。把跨文件信息合并成直接给出的答案，可能消除原测试点。
- 改变目标、规则、信息出现时机或工具语义时，重新推导预期。原检查脚本是否仍适用须明确说明。
- 若补强原判定器，分别列出原判据与拟新增判据；不要声称新增部分已有原基准验证。
- 找不到合适来源时先标覆盖缺口，再按本次授权决定是否补充设计。补充设计与直接复用、适配分开标识。

每条入选案例用五组信息表达即可，避免重复公共环境与规则：

1. **名称、类别与主要目的**：用户需求任务注明对应需求及依据；具体能力专项注明目标性质与关键条件，按需关联另一类案例。完整/局部任务、单轮/多轮另行描述，不代替这两类。
2. **用户任务**：被测 Agent 实际收到的请求；保留重要原意，翻译或改写需注明。
3. **初始材料与必要条件**：具体来源、版本、初始状态、工具、交互或反馈条件；清楚区分已提供和待准备。
4. **预期与判定证据**：完成条件、允许的合理替代方案、证据重心和位置、尚无法判断的部分。
5. **来源与适配说明**：原案例定位、复用条件、采用理由、修改内容及待核对项。

只有任务需要时才增加多轮消息、异常触发或恢复条件。不要强制填写难度、目标错误、失败根因、检出证明或统一通过阈值。

## 6. 按具体判据选择结果与过程证据

区分**预期依据**（为什么这样才对）与**运行证据**（实际发生了什么）。设计阶段只描述未来需要取得的运行证据，不伪造执行结果。

- 成果要求可由最终文件、回答或实际状态判断时，以结果为主，允许不同合理路径。
- 参数、交互、顺序、授权、资源或停止要求，需要相应的可观察过程记录。
- 判断在异常、中断或信息更新后是否完成任务，通常需要条件确实出现的过程证据和最终结果。

过程只包括可见消息、工具输入输出、执行事件、状态和产物变化，不要求隐藏思维链。声明“已执行”不能单独证明外部效果；外部检查通过也不能证明 Agent 亲自验证过。

证据关联到正确运行、对象和产物版本。结果与过程约束分别判断，不自行设置固定权重。记录不完整时，对应性质标“证据不足／无法判断”；若用户明确要求交付某份记录，未交付是可单独检查的任务要求。

## 7. 在集合层取舍并交付

分别检查两类覆盖：需求任务覆盖哪些用户需求、交付要求和真实依赖；能力专项覆盖哪些性质、触发条件和边界。各自列出重复、冲突与缺口，再检查两类的关联。任务成功不能直接证明所有关联能力，专项成功也不能替代需求任务的整体完成；不自动证明跨任务泛化。

数量由筛选结果、覆盖价值和实际审阅成本决定。对明确重要的缺口继续补选；新候选已不增加实质条件，或已达到本轮约定边界时，交付当前集合并说明缺口。不要为了凑数、凑齐能力目录而降低要求，也不无边界检索。

默认报告分别展示以下内容；可以是同一报告的独立章节，也可以是两份清单加一个总览：

1. **共同范围**：项目、环境、本次目标和证据边界。
2. **用户需求任务清单**：对应需求、需求依据、案例草案、任务验收、覆盖与缺口。
3. **具体能力专项清单**：目标能力、可观察性质、关键条件、案例草案、专项判据、覆盖与缺口。
4. **关联与筛选记录**：两类如何对应；实质检查过的候选、处理决定、来源与适配记录；材料、环境和规则的待确认项。

每类都使用上述五组案例信息并保留材料定位。某类尚无合适案例时明确留缺口，不为形式对称凑数。两类的结果与结论分别报告，不默认合成一个总分。

交付前核对来源链接与版本、任务和预期的一致性、适配是否保留测试意图、证据是否支持所写结论。只有静态查阅就写“静态核对”，不写成“已运行通过”“已证明能检出问题”或“能力已验证”。

默认输出 Markdown；只有用户或平台明确需要时再转换协议。接入平台时读取实际提交合同，记录 Skill 版本和来源；合同表达不了的方法材料单独保留并说明差距，不擅自改平台或压缩掉必要信息。发布或确认版本遵循用户现有授权。

## 8. 根据使用反馈调优

让用户能指出具体的采用决定、适配内容或判据，而不只评价总体印象。优先记录：选题偏离、重复覆盖、预期依据不足、条件不可构造、证据拿不到、过程限制过死。

先修订本轮案例或测试点；反复出现的共性问题再改为 Skill 规则。认可的案例及修订理由可以作为后续范例。用户接受设计、程序格式校验通过和真实执行有效是不同结论，应分别记录。
