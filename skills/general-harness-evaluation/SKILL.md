# 通用 Harness 评测

从当前项目的关键路径和失败模式出发，交付风险清单、候选题、可执行环境、验收依据和覆盖缺口。先验证环境与判据，经人工审阅后可冻结基线。被测 Agent 的正式运行、评分和轨迹分析另行处理。

## 1. 先定评测问题和风险

用一段话写清被测项目与版本、用户要判断什么、实际可用的工具和交互方式。优先读用户需求、项目入口和已有运行记录。区分源码中实现、离线验证、真实运行三种证据。只有会影响选题的事实缺失时才查补或提问。

先列最值得测的风险，再按风险找题。每项记录「关键路径｜触发条件｜具体失败及后果｜期望行为｜判定证据」。优先覆盖会破坏关键流程、造成错误结果或难以恢复的场景。按适用性检查正常、负向和边界条件。被测对象包含 Skill 时，考虑触发、核心逻辑、产物质量和异常容错，重点放在关键分支。

- **需求任务**从明确的用户需求、可核对的历史任务或有相同使用场景的真实工程问题出发，保留原任务需要处理的依赖、约束和交付。
- **能力专项**先确定一个可观察的行为，再找能触发它的任务。可以用小型构造案例，但须说明触发条件和覆盖边界。

## 2. 先定种子题和判据，再扩覆盖

从优先风险里选一条定种子题。写清初始环境、触发动作、正确行为及其依据，再定如何区分通过、失败和证据不足。先定独立于 Agent 自述的结果检查和必要约束。至少核对判据能区分原缺陷、正确交付和一个有代表性的错误交付。条件允许时在固定环境离线验证这些对照，记录已验证和待验证的项。

按覆盖缺口选材料，并记录来源类别：

| 来源 | 怎样使用 |
| --- | --- |
| 专家设计 | 根据用户、领域负责人确认的规则和场景定种子题及验收。 |
| 规则扩展 | 关联母题，每次优先改变一个条件。只换表达时沿用判据。条件变化时按已知规则重算预期。模型可改写表达，业务规则由原契约或负责人确认。 |
| 真实记录 | 从项目问题跟踪器、支持工单、故障报告、线上记录或基准发布方原始案例取材。按风险分类抽样，同时核对出处、版本、触发材料和预期。 |
| 历史失败 | 保存已确认的失败现象、影响和证据，标记复现及修复状态。未确认的原因单列。回流后先更新风险清单，再决定是否补题。 |

记录原始链接与版本或案例 ID，分别标出保留、改写和自行构造的部分。从本地回归反推场景或重造坏版本时标为改编。选来源看原始证据和可复现性，入口可以是 GitHub、项目官网、数据集平台或工单系统。题量和来源比例按覆盖需要决定。

## 3. 为候选题准备可执行环境

按题型复用已有环境或补齐任务包。记录源码与数据版本、运行时和依赖锁、初始文件或服务状态、工作目录、工具与读写及网络权限。运行时版本与平台范围写具体。连接凭据通过运行时配置引用。

交付可调用的初始化、任务启动、自测、独立验收和重置入口，说明工作目录、参数与退出状态。依赖和路径从任务包或显式配置解析。准备阶段可以安装依赖，任务执行阶段遵守已声明的访问范围。参考修复、独立判据和运行证据保留在评测侧，写明给 Agent 暴露的材料。

在全新工作目录实际验证初始化、原问题复现、验收及重置。用原缺陷、参考正确交付和代表性错误交付检验判据，并记录重置后的初始材料哈希。服务类任务验证就绪条件、故障触发和停止清理。将环境验证与真实模型运行分别记录。

逐题标记「待适配、环境已验证、待人工审阅」及证据位置。缺依赖、初始化失败、无法复现、验收入口不可用或重置不一致时保留缺口，补齐后再冻结进基线。记录实测平台、解释器、依赖指纹、命令、返回结果及尚未验证的范围。

## 4. 审阅候选题并决定去留

| 入选门槛 | 如何判 |
| --- | --- |
| **场景站得住吗？** | 需求任务应能指出需求或案例来源，以及适配后仍保留的关键依赖。专项须有明确、可构造的触发条件。只有场景名称相似，或触发条件尚不具备，就留作候选。 |
| **Agent 要自己发现或做到什么？** | 对照能力目标，检查 Agent 实际可见的提示、文件和工具反馈。测自主定位时，题面可以给症状、复现方法与正确行为，关键定位或修复线索应由 Agent 查出。已经给出关键位置或原因时，改写题面，或改列为执行、修复、恢复等适用的专项。将参考解和评分侧材料留在评测侧。 |
| **结果能回答评测问题吗？** | 确认当前 Harness 能提供所需输入、权限和观测。写出由需求或契约支持的验收方式，允许合理替代实现。若要判断定位、修改、验证或异常恢复卡在哪，指出对应的轨迹、状态或产物。关键证据拿不到、判据分不清关键错误或预期仍不明确时，先修补或暂缓。 |

逐题给出**入选、待适配或不采用**，一句话写清依据。关键运行条件尚未核实的候选标为待适配。题量是目标，缺合格题就保留缺口。重复材料只计实际新增的测试条件。

测能力边界时，优先选可比较的题。围绕同类任务改变一个会影响行为的条件，例如增加一次有证据的编辑冲突，说明通过或失败分别能回答什么。把环境成本单列。难度标签记录设计预期和依据，实跑表现单列。

对照例：超时修复题如果已经指出两个接口和各自的单位契约，保留它来测契约修复。给同一题加一次真实可观测的并发拒绝，可以测冲突恢复。要测独立定位，另用保留复现和预期行为、需要 Agent 自行追踪实现的题。前两题共享材料，冲突对照增加的是恢复条件。

## 5. 交付评测集草案，审阅后冻结基线

分别列需求任务和能力专项。每题写两层审阅文案，另行保留实际发给 Agent 的题面。

- **列表标题与一行简介**。标题写明在哪个工程或工具里改什么。简介补上实际执行环境、工程范围或容易被改坏的行为中最能说明难度的信息。读者扫一眼要能区分现有工程里的改动和独立小脚本。
- **点开后的详情**。直接进入具体场景。写用户原本想做什么、做了哪一步、看到了什么，必要时给出实际输入和结果。用普通动作和现象表达项目内部术语。接着交代 Agent 拿到什么、在哪种环境运行、从哪里复现、要改到什么程度、怎么验证和交付。把影响验收的限制写出来，删掉重复概述。

例如列表用「修复 LangChain 的 Python 文本切分库中残留的空格」，下一行说明 Windows 上如何复现，以及改动要保留去空格开关和相邻两段共用文字的规则。详情从输入 `ab ab ab` 起笔，给出实际三段和预期三段，再写源码副本、验证命令及交付。实跑已经结束时，审阅文案与当时发出的原题面分开保存。

正文补齐风险对应关系、实际题面与初始材料、来源与必要的适配、验收与证据。将任务验收和诊断观察分开。需要看推进时，预先写出任务特有的阶段边界及其证据，例如复现失败、开始修改业务产物、修复后验证、完成交付。记录最后证实的阶段和首个未证实的关键动作，保留事件或产物位置。多轮、异常或恢复专项注明怎样确认触发。

审阅通过的核心用例可冻结为版本化基线，用于版本比较或发布门禁。冻结题面、环境和依赖、验收规则及其证据方式。候选和用于诊断的扩展单独保留。触发条件、预期或证据有缺口时回到对应风险和候选题补齐。新发现的失败先回流风险清单，审阅后纳入后续版本。

结尾只列会影响结论的缺口、未核实条件和重要取舍。默认交付 Markdown。接入平台时按实际提交合同记录 Skill 版本与来源。
