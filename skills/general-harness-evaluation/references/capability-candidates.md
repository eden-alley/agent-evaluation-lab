# 候选能力与方法来源

> 共创参考 · 2026-11-06。以下是结合一手材料整理的候选范围，不是公认的完整标准，也不是已经共同确认的必测清单。根据具体需求和被测 Harness 选择、合并或补充。

## 如何使用这些来源

确定本次维度及结果／过程证据时，结合[评测维度与证据选择](evaluation-dimensions-and-evidence.md)使用。下表按来源归纳关注点，新参考表按当前共创的能力目录组织；两者不是两套需要分别覆盖的配额。

来源说明某类行为为什么值得关注；项目需求、工具约定与明确状态规则决定具体预期。表中的“判定所需材料”是生成案例时要规划的观察方式，不代表已经取得运行证据，也不要求本 Skill 去运行或评分。

| 候选能力 | 适用与设计重点 | 方法来源 | 生成时需要说明的判定材料 |
|---|---|---|---|
| 工具调用与多步执行 | 项目支持工具调用时，检查参数、依赖关系、工具结果回填与后续使用；区别模型选择行为和 Harness 的实际派发行为 | [S1]、[S2] | 所需工具定义、输入输出、关联关系，以及任务所需的最终状态 |
| 信息不足与能力边界处理 | 区分能够通过工具查到的信息、必须询问用户的信息，以及当前没有可用工具的任务；具体处理由项目约定决定 | [S2] | 当时可见的信息和工具、用户补充条件、允许的下一步行为 |
| 上下文与跨轮状态保持 | 后续操作应基于最新有效信息；压缩、跨会话记忆等只在项目有此能力或承诺时设计 | [S1]、[S2]、[S3] | 前后轮的关键事实与状态、信息更新点、后续动作需使用的值 |
| 异常处理与恢复 | 针对项目会遇到的异常设计；重试、修正、替代或停止依照工具及项目策略，不能统一规定必须重试 | [S2]、[S4] | 可构造的异常、实际操作是否已经生效的条件、允许的恢复结果及副作用约束 |
| 任务推进与完成判定 | 对多步骤或持续任务，检查最终产物是否满足要求，完成声明是否有相应结果支撑 | [S3]、[S4] | 任务完成条件、需要检查的产物或状态、过程与结束条件 |
| 资源与执行边界 | 项目明确规定步数、时间、预算或取消行为时，才据此生成边界测试；没有约定阈值时不自行定义低效 | [S4]、[S5]及项目契约 | 明确限制、计数或计时口径、触发条件和预期停止行为 |

子 Agent 协作、持久记忆、权限控制等可按需求增加；引用到这些机制的文章不意味着所有 Harness 都必须实现它们。

## 一手来源及其支持范围

### S1 · LangChain：The Anatomy of an Agent Harness

[原文](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)

用于理解 Harness 可能包含的工具执行、状态、上下文管理和编排等组成。该文是作者的工程观点，不是通用评测能力标准。

### S2 · Berkeley：BFCL V3 多轮与多步工具调用

[原文](https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html)

提供多步依赖、多轮信息、缺参数、缺工具、长上下文等设计参照，并使用 API 状态检查。这里引用其设计方法，不使用旧版排行榜分数，也不把函数调用基准等同于完整 Harness 评测。

### S3 · Anthropic：Effective harnesses for long-running agents

[原文](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)

记录长任务中的跨会话信息丢失、进度延续、过早宣告完成和验证不足等问题。其具体方案来自长时编码任务，迁移到其他 Harness 需要结合项目条件。

### S4 · Anthropic：Demystifying evals for AI agents

[原文](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

用于区分输入、轨迹和环境结果，设计清楚的成功条件并允许合理替代方案。该文也说明 Agent 评测通常包含模型与 Harness 的共同表现。

### S5 · Anthropic：Writing effective tools for agents

[原文](https://www.anthropic.com/research/writing-tools-for-agents)

提供任务现实性、可验证结果，以及耗时、工具次数、token 和工具错误等观察维度。资源阈值和停止规则仍须来自当前项目，不能由该文章推定。

## 归因边界

生成案例时说明测试对象和可观察结果即可，不提前给出“模型问题”或“Harness 问题”的结论。固定模型输出的程序测试与真实模型参与的任务测试可以分别设计；两者的证据能力不同，不能互相替代。
