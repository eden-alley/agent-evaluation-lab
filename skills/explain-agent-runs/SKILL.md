# 任务过程讲解

让读者看懂题目要求、Agent 实际做了什么、关键结果及停止位置。用已有运行材料完成讲解，保留证据出处。将额外执行、付费模型调用和代码修改放在相应授权下进行。

## 先确认讲的是哪次运行

核对批次、完成时间、题目版本、模型及运行次数。用户问“最新一批”时按实际完成时间和题量确认。题目编号可能跨批次重复，同一题的重跑或继续运行分别注明。保留原题面与当前有效的判定，核对历史自动值及后续复核的差异。

先读题面、最终结果和交付清单，再沿关键事件回读轨迹。原始文件与平台记录能对应时核对文件指纹。取证遇到缺口时写清缺少哪段材料。

## 用普通话说明题目

先交代用户原本想做什么、看到什么问题、希望改成什么样。给出最能说明问题的输入和预期结果。说明 Agent 得到的源码、文件或服务，以及影响完成要求的限制。

使用正式项目名和直白描述。专业术语首次出现时解释含义。题目编号仅用于查找，例如写“第 U02 道题要求修复文字切分后多出来的空格”。正文优先描述可见行为和结果。

## 按关键进展讲过程

从复现问题、首次修改、检查结果、修改方向变化、额外调查、写报告及停止等节点划分段落。把连续读文件、反复打印结果等动作合并，说明这段时间在查什么、得到了什么反馈、后来怎样继续。段落数量按实际进展决定。

每段按“动作 → 实际反馈 → 后续动作”组织。写“它写了一个小程序检查结果，参数错误后又修改这个小程序”，让读者知道时间具体花在哪里。工具名称或次数只在有助于理解时出现。

说明计数口径。用“第 N 次回复”时按原记录中的模型回复计数，一次回复可以包含多个操作。事件编号保留在证据引用里。没有可靠对应关系时用先后顺序，避免推算。

描述动作用证据能支持的词。临时文件与实现功能的源码分别核对。发现修改后检查失败时，讲清新错误是什么；后半段追查新增问题或修理自己的检查程序时，说明问题范围怎样变化。用时间范围和关键反馈说明反复操作。

以记录为依据介绍发生了什么。模型的想法、动机或能力原因需要另外的证据。静态查代码、讲解者另做的检查、Agent 自己执行以及评测程序执行，分别注明来源。

## 解释结果和停止位置

逐项核对功能行为、指定检查、交付说明、文件范围等原要求。说明哪些已完成、哪些未满足，以及它们怎样形成当前结果。

- 功能检查已通过但缺少报告、指定检查或清理时，保留功能通过的事实，指出具体未交付事项。
- 功能与报告均已完成，但违反原文件保留要求时，说明实际改了什么。
- 工具退出码为 0 而正文显示失败时，按两项事实说明。核对真正的检查结果。
- 明确区分 Agent 成功运行过检查、评测程序后来检查通过，以及当前没有足够记录判断。
- 到达次数上限时，说明最后完成的动作和仍未完成的关键工作。正常结束、被迫停止和检查程序异常分别记录。

完成说明里写错事实时，对照原始记录指出差异。原因尚未确定时，保留可确认的失败现象和待查问题。用户进一步要求改进建议时，再关联相应复盘方法。

## 交付和核对

多题先用一小段说明批次范围及整体结果，再按用户关注点选择案例。每题依次写题目背景、分段经过、最终结果及证据链接。默认使用连贯段落，阶段较多时用简短列表。

发出前逐项核对题目版本、计数、关键动作、文件变化和测试结论。主文保留足够的背景，使读者不打开原始轨迹也能理解。证据链接放在相应段落或案例之后，支持继续回查。

经过用户认可的写法见 [三道失败题的讲解示例](references/examples.md)，关键事件和文件指纹见 [示例证据](references/evidence.json)。示例属于 2026-11-12 的同一批 20 道题。
