# 运行复盘与改进候选

从已经发生的运行中找出值得修正的工作条件，交付按影响和证据排序的候选清单。输入为固定题面、验收规则、运行配置、逐项判定及原始证据。先读原始材料，核对评分结论。默认止于候选和验证设计，采纳及执行沿用用户授权。

## 核对运行与停留位置

记录任务、运行及方法版本，工具权限、预算和执行环境。核对初始材料、最终产物、测试回显及事件顺序。区分被测模型动作、执行器动作、独立验收和历史复核。

用任务自身的依赖划分阶段，指出最后证实的阶段，以及接下来缺少证据或未完成的关键动作。需要区分「没有做」和「记录没有采到」。给出可定位的事件、文件或对象。以可见行为为依据。

长轨迹先找首次实质改动、测试、异常、反馈、交付及停止事件，再回读有关区间。连续查阅可以合并成自然语言工作记录，保留范围和引用。

## 查找有价值的改进候选

只选有本次证据支撑的方向，先核对项目已有实现与检查入口。

| 方向 | 要核对的问题 |
| --- | --- |
| 导航 | 查找哪段信息花费了多次操作？入口、模块关系或文档指针是否缺失？ |
| 自动检查 | 已有自测、类型检查、范围检查或 CI 是否实际运行？检查缺失、未接线、失效分别记录。 |
| 规范与指令 | 固定语法、禁用 API、文件位置或写入范围等能否由程序检查？风格及跨文件一致性等判断交给相应审阅环节。 |
| 工具成本 | 是否反复传输大段无关信息？按范围读取、摘要及按需取原文能否保留必要证据？ |
| 信息获取 | 哪个服务状态、日志、契约或工具反馈未提供，影响了后续动作？ |
| 无效规则 | 哪条指令重复、冲突或没有改变行为？能否删减或改为按需查阅的说明？ |

对机械错误优先考虑确定性检查。对当前已有能力提出接线或修复建议，避免重复建设。把测试、环境或评分器的问题单独关联到评测侧。存在多个合理解释时保留可区分的候选。

## 交付可验证的候选

每个候选写清以下信息，可按任务复杂度合并表达。

- **观察与影响**。具体失败或工作成本，最后证实的阶段及证据。
- **解释与状态**。已经直接证实的原因，或待检验的原因假设，以及其他可能解释。
- **最小改动**。对应的工具、检查、文档或执行流程，已有实现是否可复用。
- **验证与回归**。怎样区分改动有效和无效，检查什么结果、约束及新增成本。

排序综合任务后果、覆盖范围、证据充分程度和验证成本。允许结论为当前材料不足以提出有价值的改动，列出缺少什么。

程序检查的改动用固定的正确、错误及合理替代样本验证。要检验 Agent 行为的变化，固定题面、环境、模型、判据和预算，优先一次改变一个因素。单次运行保留其范围，需要评估波动时再设计授权内的重复运行。调用次数和 Token 只是观察项，交付和明确约束仍按原验收判断。

## 反馈到评测与开发

将确认的失败现象、候选改动、验证状态和回归需求关联保存。采纳的改动经验证后进入相应工具或检查流程；新发现的覆盖缺口交回评测集生成流程审阅。更改基线或判据时建立新版本。
